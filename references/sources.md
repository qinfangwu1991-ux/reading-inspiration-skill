# 来源适配器：`scripts/fetch_source.py`

拍照之外的第二、第三个入口：**链接**和**粘贴**。脚本只负责「取到干净正文」，切段仍由 Agent 读正文后做。

## 路由表

| 来源 | 怎么取 | 备注 |
|---|---|---|
| 微信公众号 | curl + HTML 抽取 | 正文容器 `#js_content`，`<p>` 分段，格式最规整 |
| 博客 / 新闻 / 一般网页 | 同上，"文本量最大的容器"当正文 | 找不到明确容器时全页块 + 页头裁剪 |
| 飞书文档 / 知识库页 | `lark-cli docs +fetch --doc <token> --as user` | 返回的是 HTML 风格字符串（`<b>/<blockquote>/<h2>`），复用同一个抽取器，`structured=True` |
| 乐享页面 | **脚本不处理**，退出码 4 | 必须由 Agent 用 MCP `block_fetch_page` 取，再 `--from-text` 交回 |
| 本地 md / txt / html | 直接读 / 抽取 | — |
| 本地 docx | `zipfile` 读 `word/document.xml`，按 `<w:p>` 取段落 | 不依赖 python-docx |
| 本地 pdf | `pdftotext -layout` | 没有该命令时提示走 workbuddy-pdf |
| 用户粘贴的文字 | `--from-stdin` | 不抓取、不判断长度 |
| 小红书（`xhslink.cn` 短链 / `xiaohongshu.com`） | **先桌面 UA，抓不到再换手机 UA 重抓** | 桌面 UA 会被 302 到 `/login?redirectPath=…`，页面里空的；手机 UA 直接给完整笔记正文。见下面第四节 |

## 退出码（Agent 按这个决定下一步，别硬试）

| 码 | 含义 | 该做什么 |
|---|---|---|
| 0 | 成功 | 切段 |
| 2 | 参数 / 文件问题 | 修参数 |
| 3 | 网络或 HTTP 失败 | 重试一次，仍失败按 5 |
| 4 | 乐享页面，需 MCP | 用 `block_fetch_page` 取正文后 `--from-text` |
| 5 | 正文太短 / 要登录 / 靠 JS 渲染 | **让用户把正文粘过来**，不要反复换抓法 |

## 抓取质量的五个坑（都实测踩过）

1. **容器选择 vs 页头裁剪是两个独立开关，别混**

   - 网页：先选「文本量最大的容器」，再用 `_looks_like_nav` 裁掉页头（账号名、分类、面包屑）。
   - 飞书 / docx：它们常有多个并列区块，取「最大容器」会**静默丢掉一半内容**；同时开头就是真内容，**不能裁头**。
   - 判断依据是**来源类型**，不是「有没有找到容器」。早期按容器判定，结果公众号顶部混进了「大华大华粥左罗 / 在小说阅读器读本章」，飞书文档反而被裁掉了正文开头。

2. **页头裁剪必须"conservative"**：只裁「短且不含任何标点」的块。
   正文哪怕很短通常也带标点（「这是一个关于选择的故事。」），所以这条规则能去掉「周刊」「封面图」这类栏目名，又不会吃掉真正的短开头。

3. **中文段落之间的空格要删**：HTML 源码的换行缩进会被压成一个空格，中文正文会出现「文字 文字」。
   `norm_ws()` 在空白归一化后，把「CJK 字符 + 空格 + CJK 字符」之间的空格去掉，只保留中英文之间的空格。

4. **`<title>` 会被 `head` 吃掉（2026-10-25 百度新闻实测）**：`head` 在 `SKIP_TAGS` 里，
   而 `handle_data()` 早期先判 `skip_depth` 再判 `_in_title`，导致 `<title>` 永远读不到，
   标题退化成「未命名文档」，段落数也数进整页页脚（36 段 vs 真实 10 段）。
   → `_in_title` 的判断必须放到 `skip_depth` 之前。

5. **新闻站的「媒体行 / 页脚 / 配图注脚」要按来源剥**（`web=True` 才剥，飞书/docx 不剥）：
   - `MASTHEAD`：`2026-10-22 17:11九派新闻官方账号`、`关注`、`记者xxx` —— 排在标题后、正文前，不剥会把段号整体顶歪 3 位
   - `FOOTER`：`举报/反馈`、`微信好友`、`新浪微博`、`复制链接`、`扫码分享`、`百度APP扫一扫`、`关于百度`、`京ICP…`、`顶部` —— 从尾巴往回剥，遇到第一句真正文就停
   - `FIGCAP`：`阿宇将农村破屋打造成实验室。图/恩施州融媒体中心杜瑞芳` —— 配图注脚不是正文，
     留着用户照段号挑会挑错段（实测 36 → 12 → 10 段）
   - 页头剥行有上限：最多 5 行、累计 120 字以内，防止连着把真正文开头削掉

## 四、抓不到正文时的两级兜底（2026-10-25 实测小红书）

1. **换手机 UA 重抓**（首选，能拿到完整正文）
   小红书桌面 UA → `302 /login?redirectPath=…`，页面 36KB 全是脚本，正文 0 字；
   换 `MOBILE_UA`（iPhone Safari）→ 200，直接给出完整笔记正文，还带分段。
   - 顺带修正记录链接：桌面端 `final` 是登录页，要用手机端的 `final`，否则卡片 `url` 会存成一串 `redirectPath=%3F…` 的编码垃圾
2. **页面摘要兜底**（`meta_article()`）
   正文只存在于 `og:description` / `description` 的站点，用 meta 当正文；会把被压平的分行还原：
   孤立 `" . "` → 段落分隔，`1️⃣`/`①` 这类序号前断段，结尾话题标签串单独成段。
   代价：**摘要可能被平台截断**，脚本会在 stdout 明确警告，切段前先看结尾是否完整。

配套的两条噪声规则（只在网页路径 `trim_head=True` 时生效，别拿去套飞书/docx）：

- `UI_NOISE`：发布日期 `08-17`、`点击右上角…`、`说点什么…`、`App内打开`、连续话题标签串
- **纯数字只在结尾剥**（`tail_strip_numbers` 逻辑）：点赞数 `35`/`53` 在尾部，但公众号文章的小节号 `01`–`05` 在正文中间 —— 早期把「纯数字」写进 `UI_NOISE`，公众号直接少了 5 段（实测 170 → 165），差点静默丢内容

## 为什么不用 bs4 / readability

本机（以及别人的干净环境）不保证装了 `bs4` / `lxml` / `html2text`。整个脚本只用标准库：
`html.parser.HTMLParser` 收集块 + 容器长度统计，`urllib.request` 抓取，`zipfile` 读 docx。
好处是解压即用；代价是没有 readability 那么聪明，所以上面三条坑必须靠规则兜住。

## 已知限制（如实告知，别假装能抓）

- 依赖 JS 渲染的站点（知乎专栏、Notion、部分企业站点）curl 拿不到正文 → 退出码 5
- 需要登录的文档（付费墙、内网系统）同理
- 默认截断 20000 字（`--max-chars` 可调），超长文档只能按章节分段处理
- 飞书文档读取依赖 `lark-cli` 已登录；没装或没登录时明确报错，不静默降级
